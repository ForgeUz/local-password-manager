## D10 — P2P Sync with Offline Peering (P0)

### Why this is P0
Mobile users need sync, but cloud sync violates zero-cloud doctrine. P2P is the only doctrinally-compliant solution. Offline peering makes it practical for users without constant internet.

### Threat Model (honest limitations)

**What P2P protects:**
- No central server sees encrypted blobs
- Noise protocol provides forward secrecy
- PSK (pairing passphrase) prevents MITM
- Devices must be physically close (BLE/WiFi Direct/local network)

**What P2P does NOT protect:**
- Physical access to both devices (if attacker has both)
- Malicious device pretending to be trusted peer (mitigated by TOFU pinning)
- Compromised pairing passphrase (user's responsibility)

**Offline peering risks:**
- Devices must be in same physical space (BLE/WiFi Direct range ~10m)
- Special sync password (≥8 chars, alphanumeric) required
- If password is weak/leaked, attacker in range can sync
- **Mitigation:** Use Argon2id(password, salt) to derive PSK (raises offline dictionary cost)

### Architecture

**Layer 1: Transport**
- Android: Nearby Connections API (BLE + WiFi Direct)
- Linux: Avahi/mDNS for discovery, TCP for transfer
- Fallback: Local network (same WiFi) if BLE unavailable

**Layer 2: Pairing (one-time setup)**
```
Device A generates 8-char alphanumeric passphrase
Device B enters passphrase
Both derive PSK = Argon2id(passphrase, shared_salt)
Noise NNpsk0 handshake
TOFU: pin peer's static key
```

**Layer 3: Sync protocol**
```
1. Both devices connect (BLE/WiFi Direct/local network)
2. Authenticate via pinned peer key (TOFU)
3. Exchange encrypted vault diffs (not full vault)
4. Each device applies diff locally
5. Verify sync via HMAC(vault_hash, sync_key)
```

**Layer 4: Conflict resolution**
- Last-write-wins with timestamp (HLC: Hybrid Logical Clock)
- User can manually merge conflicts
- Deleted entries stay deleted (tombstones with TTL)

### UI Flow

**Initial pairing:**
1. Settings → Sync → Enable P2P Sync
2. "Generate pairing code" → 8-char alphanumeric passphrase
3. Show passphrase on screen (large text, easy to read)
4. On second device: enter passphrase
5. "Pairing successful. Peer device trusted."

**Ongoing sync:**
1. Devices discover each other (BLE/WiFi Direct)
2. Notification: "Sync with [Device Name]?"
3. User confirms → sync proceeds in background
4. Notification: "Sync complete"

**Honest limitations (displayed in UI):**
- "Both devices must be physically close (same room)"
- "If you lose both devices, your data is gone. This is by design."
- "Sync password must be kept secret. If leaked, someone nearby could sync with your device."

### Test Plan

| Test | Description |
|------|-------------|
| Pairing success | Generate code, enter on second device |
| Pairing failure | Wrong code → error after 3 attempts |
| TOFU pinning | First handshake pins key, second handshake verifies |
| Sync diff | Add entry on A, sync, verify on B |
| Conflict resolution | Edit same entry on both, verify LWW |
| Offline peering | Devices in different rooms → no discovery |
| MITM prevention | Fake peer → handshake fails |

## D11 — Security Tiers (P1)

### Why this is P1
Users have different security needs for different accounts. Bank ≠ streaming service. Tiers allow progressive security without overwhelming users.

### Tier Definitions

| Tier | Examples | Unlock Method | Autofill |
|------|----------|---------------|----------|
| **Standard** | Social media, forums, streaming | Biometric only | Auto (with domain match) |
| **Sensitive** | Email, cloud storage, shopping | Biometric + re-auth after 5 min | Auto (with domain match + lookalike check) |
| **Critical** | Banking, crypto, government | Master password + biometric + TOTP | Manual (user must type password) |

### Implementation

**Per-entry tier assignment:**
```dart
enum SecurityTier { standard, sensitive, critical }

class V4VaultEntry {
  final String domain;
  final String username;
  final SecureBuffer password;
  final SecurityTier tier;
  // ...
}
```

**Default tier assignment:**
- Auto-detect based on domain (bank → critical, netflix → standard)
- User can override per entry
- New entries default to "standard" unless auto-detected

**Tier enforcement:**

| Action | Standard | Sensitive | Critical |
|--------|----------|-----------|----------|
| Vault unlock | Biometric | Biometric | Master password |
| Autofill | Auto | Auto (with delay) | Manual |
| Reveal password | Tap to show | Tap + biometric re-auth | Type master password |
| Edit entry | Biometric | Biometric | Master password |
| Export | Allowed | Allowed | Blocked |

**UI indicators:**
- Color-coded badge on each entry (green/yellow/red)
- Tooltip explaining tier requirements
- Bulk tier assignment for imported entries

### Test Plan

| Test | Description |
|------|-------------|
| Default assignment | Import bank.com → auto-assign critical |
| Override | User changes critical → standard |
| Reveal enforcement | Critical entry → requires master password |
| Autofill enforcement | Critical entry → manual only |
| Bulk assignment | Select 10 entries → assign tier |

## D12 — TOTP Generator (P2)

### Why this is P2
Many services require 2FA. Built-in TOTP eliminates need for separate apps (Google Authenticator, Authy). RFC 6238 compliance is standard.

### Architecture

**Storage:**
```dart
class TOTPConfig {
  final String issuer;        // e.g., "GitHub"
  final String accountName;   // e.g., "user@example.com"
  final SecureBuffer secret;  // base32-encoded secret
  final int digits;           // 6 or 8
  final int period;           // usually 30 seconds
  final String algorithm;     // SHA1 (default), SHA256, SHA512
  
  TOTPCode currentCode() {
    // RFC 6238: HMAC-SHA(algorithm, secret, floor(time / period))
    // Truncate to last `digits` decimal digits
  }
}
```

**Import methods:**
1. **QR code scanner** (otpauth:// URI)
2. **Manual entry** (issuer, account, secret)
3. **Bulk import** (from other TOTP apps via export file)

**Display:**
- Current code (large, easy to copy)
- Countdown timer (circular progress)
- Next code (small, preview)
- Copy to clipboard (auto-clear after 30s)

**Honest limitations:**
- TOTP secrets stored in vault (encrypted with DEK)
- If vault compromised, all TOTP codes compromised
- Recommend: use hardware tokens (YubiKey) for critical accounts

### Test Plan

| QR import | Scan otpauth:// URI → verify code |
| Manual entry | Enter secret → verify code |
| Countdown timer | Code changes every 30s |

## D13 — Per-Site Passkey Generation (P3)

### Why this is P3
Passkeys are the future of authentication. Vault can generate and store passkeys per site, eliminating phishing and password reuse.

### Architecture

**Storage:**
```dart
class PasskeyEntry {
  final String domain;
  final String rpId;          // relying party ID
  final SecureBuffer credentialId;
  final SecureBuffer privateKey; // P-256 or Ed25519
  final String publicKey;     // for verification
  final DateTime createdAt;
}
```

**Generation flow:**
1. User visits site (embedded WebView)
2. Site requests passkey via WebAuthn API
3. Vault intercepts request
4. Generate P-256 keypair
5. Store private key in vault (encrypted)
6. Return public key to site
7. Site stores credential ID + public key

**Autofill flow:**
1. User visits site
2. Site requests passkey authentication
3. Vault retrieves private key (decrypt with DEK)
4. Sign challenge with private key
5. Return signature to site
6. Site verifies signature

**Honest limitations:**
- Passkeys stored in vault (single point of failure)
- If vault compromised, all passkeys compromised
- Recommend: use hardware tokens for critical accounts
- Platform-specific: Android Keystore for key storage (preferred), fallback to vault

### Platform Integration

**Android 13:**
- Use Android Keystore for private key storage
- Biometric authentication for key access
- Hardware-backed if available (StrongBox)

**Fallback:**
- Store encrypted private key in vault
- Decrypt on demand with DEK
- Less secure, but works everywhere

### Test Plan

| Test | Description |
|------|-------------|
| Passkey generation | Generate on test site → verify stored |
| Passkey authentication | Authenticate on test site → verify signature |
| Android Keystore | Verify key stored in Keystore (hardware-backed) |
| Fallback | Verify encrypted storage works |
| Domain isolation | Passkey for site A ≠ site B |

## D14 — Android Autofill Service (P4)

### Why this is P4
Android 13 has mature Autofill Service API. Native integration provides seamless UX.

### Implementation

**AutofillService.kt:**
```kotlin
class VaultAutofillService : AutofillService() {
    override fun onFillRequest(request: FillRequest, callback: FillCallback) {
        val domain = extractDomain(request.structure)
        val entries = vault.search(domain)
        
        // Domain matching (phishing protection)
        for (entry in entries) {
            if (entry.domain != domain) {
                // Lookalike check
                if (isLookalike(entry.domain, domain)) {
                    // Hard-stop: refuse to autofill
                    callback.onSuccess(null)
                    return
                }
            }
        }
        
        // Build FillResponse with SaveInfo
        val response = buildFillResponse(entries, request.structure)
        callback.onSuccess(response)
    }
}
```

**Digital Asset Links:**
- `assetlinks.json` on user's domain (if applicable)
- Verify app ↔ domain association
- Prevents phishing (only trusted app can autofill)

**Security tier enforcement:**
- Standard: auto-fill
- Sensitive: auto-fill with 5s delay + re-auth prompt
- Critical: manual fill only (user must type)

## What We Chose (and What We Didn't)

**Chose:**
- P2P sync over cloud sync (doctrine alignment)
- Security tiers over one-size-fits-all (usability)
- Built-in TOTP over external app dependency (convenience)
- Per-site passkeys over single master passkey (phishing resistance)
- Android 13 native APIs over cross-platform hacks (stability)

**Didn't choose:**
- Cloud sync (violates zero-cloud)
- Vendor-controlled recovery (violates zero-recovery)
- Weaker crypto for performance (violates no-home-rolled-crypto)
- Overwhelming users with all features at once (progressive disclosure)

**Deferred (not rejected, just later):**
- TPM sealing (requires hardware, not critical for mobile-first)
- Runtime attestation (advisory, low priority)
- Post-quantum sync (requires liboqs, research ongoing)

**Rejected:**
- Cloud-based sync relay (violates doctrine)
- Single master passkey for all sites (phishing risk)
- Automatic TOTP code filling (security risk)
- Weaker security for convenience (doctrinal violation)

## Honest Limitations (V6.5)

1. **P2P sync requires both devices online simultaneously** — no async sync
2. **Offline peering limited to physical proximity** — can't sync remotely
3. **Security tiers are advisory** — determined user can bypass
4. **Passkeys stored in vault** — single point of failure
5. **TOTP secrets stored in vault** — if vault compromised, all codes compromised
6. **Android Autofill Service can be disabled** — user can bypass security
7. **Material 3 theming limited** — Flutter constraints

These are not bugs. They are trade-offs. Users must understand and accept them.
