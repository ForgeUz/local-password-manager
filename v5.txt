################################################################################
PART 1 — V5: THE PERFECT FINAL FORM
################################################################################

V5 is not new features. V5 is v4 with every contradiction removed, every false
claim replaced by a true one, and every mechanism made internally consistent.
The feature surface stays identical; the correctness surface becomes total.

1.0 DOCTRINE (ABSOLUTE INVARIANTS — UNCHANGED, NOW ENFORCEABLE)
--------------------------------------------------------------------------------
  - Zero-cloud: only egress is opt-in breach monitoring (prefix-only or
    offline corpus). No server, no relay, no telemetry.
  - Zero-trust: every input (MP, TOTP, backup code, PIN, peer, clock, file)
    is treated as hostile until math proves otherwise.
  - Zero-recovery-by-design: no backdoor. Inheritance is opt-in and fully
    self-custodied. Vendor sees nothing, holds nothing, can assist nothing.
  - Smart over More: every feature justifies its byte count. Kill switches on
    every v4/v5 feature; features that out-cost their value get deleted.
  - Honest limitations: every residual risk is stated in the UI in plain
    language. No false enforcement claims anywhere in spec, UI, or docs.
  - No home-rolled crypto: audited bindings only (libsodium FFI, PQClean).
  - Sync optional: removing the entire sync module leaves a fully working
    offline password manager.


1.1 CORE CRYPTOGRAPHY (FINAL FORM)
--------------------------------------------------------------------------------
  - libsodium via dart:ffi, pinned, startup self-test, fail-closed.
  - Native HKDF-SHA256 via crypto_kdf_hkdf_sha256_{keygen,extract,expand},
    symbol-probed at startup; RFC 5869 known-answer tests; NO hand-rolled
    HKDF anywhere in the codebase.
  - Argon2id adaptive calibration: target 500–1000 ms desktop / 1500 ms
    mobile per derivation; hard floor 64 MiB / 3 iterations / parallelism
    min(4, cores). In v5 with dual-derivation unlock, each derivation is
    calibrated to HALF the target so total unlock latency stays in envelope.
  - AES-256-GCM everywhere; fresh CSPRNG 96-bit nonce per operation;
    10k nonce-uniqueness verified.
  - Constant-time comparison for every tag, MAC, and secret check.
  - Native secure memory (sodium_malloc/mlock/memzero); secrets never in Dart
    String or GC-managed Uint8List; explicit zero-wipe on lock / auto-lock /
    background / termination / entry-delete.
  - Key hierarchy: MK = Argon2id(MP, salt) · VRK = HKDF(MK, GENESIS-VRK-v4) ·
    SearchKey = HKDF(VRK, GENESIS-SEARCH-v4) · MK_duress =
    Argon2id(duressMP, SAME salt) · VRK_duress = HKDF(MK_duress,
    GENESIS-VRK-DURESS) · TokenKey = HKDF(VRK, GENESIS-LIVENESS-v5) [new].
  - MK never used directly as a cipher key. VRK wraps DEKs only. Each entry
    has its own CSPRNG DEK; entry JSON encrypted under DEK_i; destroying one
    DEK shreds exactly one entry.


1.2 FILE FORMAT GEN4+ (SINGLE FILE, STRUCTURALLY DENIABLE)
--------------------------------------------------------------------------------
  - One file. Magic GEN4, version byte, KDF params block, ONE 16-byte salt,
    12-byte nonce, vault_count = 2 ALWAYS.
  - Slot 1 = primary vault. Slot 2 = decoy vault if deniability enabled,
    CSPRNG bytes otherwise. Identical structure in both cases. No separate
    decoy file exists anywhere on disk — never.
  - Per-entry record: UUID, tier, wrapped DEK (self-contained nonce),
    search_tags (bucket-padded, see 1.8), vector clock, size-bucketed
    ciphertext.
  - Header MAC = AES-256-GCM with EMPTY plaintext over the entire header as
    AAD. The 16-byte tag IS the header authentication. No ambiguity: two
    implementers cannot diverge.
  - No v3-file compatibility branch. GEN4 or reject. Single-pass, no dead
    reader code.
  - Duress feature presence is undetectable from the file: one salt either
    way, two slots either way, slot 2 is noise-or-decoy, GCM fails on noise.


1.3 UNLOCK, 2FA, KEY COHERENCE (FINAL FORM)
--------------------------------------------------------------------------------
  - Unlock ALWAYS performs both Argon2id derivations (primary + duress
    candidate) and both GCM checks, then selects. Constant total time. No
    timing oracle for which vault opened.
  - KDF-bound TOTP: MK_full = HKDF(Argon2id(MP,salt) || SecondFactorMaterial).
    Wrong/absent second factor = wrong key = GCM failure. Math, not a check.
    Verified by calling decrypt directly, bypassing UI.
  - Backup codes COHERENT with KDF-binding (the v5 fix): SecondFactorMaterial
    is stored encrypted under MK_base (the pre-second-factor key) in a file
    outside the vault. A valid backup code (Argon2id-hashed, single-use,
    rate-limited) authorizes release of SFM into the KDF. Vault opens via the
    real derivation path. Immediate forced 2FA re-setup. MP change
    re-encrypts the SFM file. No bypass branch exists in the code.
  - 10 single-use backup codes, shown exactly once, stored outside vault.
  - Companion-device push approval: number-matching (two-digit challenge,
    three options), explicit context, rate-limited, excess silently dropped.
  - Stored TOTP for third-party accounts with undismissable co-location
    warning; ±1 step clock-skew tolerance; 30s countdown ring.
  - FIDO2 hardware key as unlock factor (P-256 signature into HKDF,
    keylogger-immune).
  - MP change is an ATOMIC event: re-wrap all DEKs under new VRK, recompute
    all search_tags, rewrite header + all payloads in one temp-file-then-
    rename save. No lazy "fix on next unlock" mixed state.
  - MP change does not reset 2FA (seed untouched) — documented.


1.4 COERCION RESISTANCE AND DENIABILITY (COMPLETE PROTOCOL)
--------------------------------------------------------------------------------
  - Honeypot canaries: 3 realistic fake entries seeded at vault creation,
    invisible in UI, internal flag only in decrypted JSON. Any ACCESS (reveal,
    autofill, copy, sync read) triggers: lock → forensic log → alert ALL
    paired devices → warning on next unlock. Internal random-subset
    decryption of canaries does NOT trigger. Zero runtime cost when idle.
  - Duress MP: opens decoy vault indistinguishably. Silent alert to all
    paired devices. Critical-tier shred scheduled (default 2 h). Adaptive
    posture frozen in duress state. Behavioral biometrics disabled. Canary
    checks suspended. Auto-lock still active.
  - CRITICAL SHRED SEMANTICS DEFINED (v5): Critical DEKs are Shamir-split
    across paired devices, so duress shred is a GROUP OPERATION.
    SHRED_SCHEDULED broadcasts to all share holders; each device destroys its
    share at the deadline. Critical becomes unrecoverable when surviving
    shares < K. Under default 2-of-3, two destroyed shares suffice; all are
    scheduled.
  - Cancellation: 8-digit code only. No session-path cancellation (the decoy
    session cannot cancel). Code stored Argon2id-hashed, rate-limited
    (3 attempts → full duress re-setup). SHRED_CANCELLED propagates to all
    devices; idempotent.
  - DEFERRAL RULE: a device executes shred only after delay AND after
    confirming no unprocessed cancellation exists from the originator. If
    offline, it DEFERS until the next successful Noise handshake or a local
    cancellation-code entry. Delay always resolves toward preservation.
  - Snapshots and conflict archive are PURGED AND RESEEDED on any DEK/share
    destruction event. Shredded material is not restorable from local
    history. Documented in the shred confirmation UI.
  - Two-vault deniability: decoy never syncs; search scoped to unlocked
    vault; export/import scoped to unlocked vault; snapshots carry both slots.
  - Honest limitation stated in UI: coercer holding BOTH passwords defeats
    the scheme; knowledge of the feature permits suspicion but never proof.


1.5 DETECTION AND ADAPTIVE LAYERS (STATISTICALLY HONEST)
--------------------------------------------------------------------------------
  - Rule-based adaptive posture, 3 deterministic rules, no ML:
      Rule 1: canary triggered → LOCKDOWN (zero-idle lock, no biometric,
              fresh MP for all autofill, Critical needs MP + FIDO2).
      Rule 2: ≥2 failed MP attempts in 5 min → HIGH (30 s auto-lock, no
              biometric, confirm-all autofill). Unknown-network escalation
              exists ONLY inside opt-in "strict roaming mode" (off by
              default) — laptops roam; permanent high posture trains users
              to disable security.
      Rule 3: known network + no failures → LOW (5 min auto-lock, biometric
              on, Standard autofill automatic).
  - Network recognition: SSID+BSSID list encrypted under VRK, wiped at lock,
    never leaves the device.
  - Behavioral biometrics (anomaly deterrent, never authentication):
      key-pair flight times in LOG-SPACE (log-normal fit via Welford —
      flight times are right-skewed, not Gaussian);
      per-pair scoring activates only after ≥8 samples for that pair;
      below the gate, a GLOBAL model with a looser 3.5σ threshold applies;
      3 consecutive anomalous keystrokes → lock + re-auth;
      disabled during duress; user kill switch; model encrypted under VRK,
      secure-memory only, timing-only (never keystroke content).
      The fabricated "0.000027%" figure is deleted; false-positive behavior
      is MEASURED in testing and reported empirically.
  - Random-subset decryption: target access decrypts ~20% of non-Critical
    entries as decoys, parallel, all wiped after use; <5 entries skip;
    Critical ALWAYS excluded. Defeats allocation-pattern inference; direct
    memory scraping remains a stated residual.

1.8 SEARCH (CORRECT THREAT MODEL)
--------------------------------------------------------------------------------
  - SSE: SearchKey = HKDF(VRK, GENESIS-SEARCH-v4); search_tag =
    HMAC-SHA256(SearchKey, normalized domain); prefix tags length 3..N.
  - TRUE privacy statement (v5): without SearchKey (requires VRK, requires
    MP), tags are opaque pseudorandom blobs. A file-only attacker learns
    entry count and — before padding — domain LENGTH (tag count = len−2).
  - Mitigation: per-entry tag lists padded to buckets (4/8/16/32/64) with
    random tags; padding collisions produce false-positive candidates,
    filtered at reveal time by decrypting the matched entry. Documented.
  - Constant-time comparison. SearchKey secure-memory only, wiped at lock.
  - Kill switch: disable SSE → full-decrypt search fallback (decrypt all,
    search, wipe). Search always scoped to the currently unlocked vault.


1.9 TIME, DEATH, INHERITANCE (REDESIGNED — MATHEMATICALLY SOUND)
--------------------------------------------------------------------------------
  - Time-locks reclassified honestly:
      (a) CPU-friction hash chain: sequential SHA-256 from a CSPRNG seed,
          calibrated on the creating device, capped at SHORT durations
          (minutes to a few hours). Used as friction only. Never claimed to
          stop a patched build or faster hardware; spec says exactly that.
      (b) Device-enforced cooldowns: signed monotonic timestamps + app
          policy for tier-downgrade cooling. Honest limitation stated.
  - Inheritance (opt-in, off by default, self-custodied):
      LIVENESS = signed epoch tokens. Every normal unlock emits a token
      (epoch++, timestamp) signed under TokenKey. Tokens propagate to heirs'
      custody: automatically to heir devices that are paired, or by manual
      export file otherwise. No server, no cloud.
      ACTIVATION = K-of-N Shamir shares + heir's latest token older than
      check-in interval + grace period (verified on heir device; heir clock
      trust documented) + short friction chain unwrap of the bundle key.
      CHECK-IN = normal vault usage; zero extra user action.
      REVOCATION = destroy metadata + re-encrypt designated entries under
      fresh DEKs + epoch invalidation. Old shares and old tokens become
      useless.
      CREATION COST: setup completes in seconds. No multi-month hash chain
      is ever computed by anyone. The calendar/CPU confusion is gone.
      UX warns when inheritance is armed and the vault has not been unlocked
      for a long time. Premature activation on long absence stays a stated
      honest limitation with generous-interval guidance.

################################################################################
PART 2 — CRITICAL ERRORS IN V4 (FULL AUDIT, 23 FINDINGS)
################################################################################

Severity scale: FATAL = cannot be implemented/defeats the feature as spec'd ·
HIGH = broken behavior or false claim in a security path ·
MEDIUM = unsound method, ambiguity, or doctrine violation.

--- FATAL ----------------------------------------------------------------------

E1. INHERITANCE TIME-LOCK CONFUSES CALENDAR TIME WITH CPU TIME
    Where: v4 §6.7 + §5.2 + §6.6
    The lock duration = check-in interval + grace (90+14 = 104 days), encoded
    as a SHA-256 chain with N = duration × hashes/sec. The creator must
    compute that chain at lock time — ~104 days of continuous CPU. Worse,
    every normal unlock "resets" the lock by computing a fresh chain. A hash
    chain encodes CPU-seconds, never wall-clock days. Phase L as written is
    unimplementable.

E2. BACKUP CODES CANNOT COEXIST WITH KDF-BOUND 2FA AS SPEC'D
    Where: v4 Phase H.1 vs H.3; §3 (v3 §12.7 carried)
    H.1: MK_full = HKDF(Argon2id(MP,salt) || SecondFactorMaterial) — the
    second factor is MATH. H.3: backup codes stored only as Argon2id hashes.
    A hash proves possession; it cannot reconstruct the TOTP seed. "Using a
    valid code disables 2FA for that session" has no possible code path: you
    cannot remove a KDF input and still derive the right key. Feature is
    spec'd into a contradiction.

E3. DURESS SALT LEAKS DURESS EXISTENCE — AND THE SPEC CONTRADICTS ITSELF
    Where: v4 §5.3 vs §4.3 vs §6.8
    §5.3 says the duress salt is stored "alongside the primary salt". §4.3
    header layout contains exactly ONE salt field. §6.8 claims the file is
    structurally indistinguishable with/without deniability. All three cannot
    hold. If a second salt appears only when enabled, header shape detects
    the feature with zero passwords. Additionally §6.8's unlock flow text
    ("try primary first; if that fails, try duress") contradicts its own
    constant-time constraint two paragraphs later.

E4. DECOY VAULT LIVES IN A SEPARATE FILE (IMPLEMENTATION DIVERGENCE)
    Where: status.md Phase J ("decoy persisted to vault.decoy") vs
    v4 §4.1/§4.3/§6.8
    The single-file, slot-2-inside-GEN4 design is the entire deniability
    guarantee. Two files on disk (vault + vault.decoy) announce the feature
    to any directory listing. Implementation defeats the spec's core claim.

--- HIGH -----------------------------------------------------------------------

E5. DURESS SHRED SEMANTICS UNDEFINED FOR SHAMIR-SPLIT CRITICAL DEKs
    Where: v4 §6.2 × v3 §19 (carried by v4 §3)
    Critical DEKs are Shamir-split (default 2-of-3) across paired devices —
    no single device holds the DEK to shred. §6.2 schedules "crypto-shredding
    of Critical-tier DEKs" locally and sends only an ALERT to peers, not a
    shred command. Destroying one local share under 2-of-3 leaves the secret
    reconstructable from the other two devices. The coercion protection
    silently does not work at default settings.

E6. SHRED / CANCELLATION PROPAGATION RACE (IRREVERSIBLE LOSS PATH)
    Where: v4 §6.2 + Phase G (message set absent)
    No SHRED_SCHEDULED / SHRED_CANCELLED messages are defined. Race: device A
    schedules shred → user escapes → cancellation sent → offline device B
    never receives it → B reconnects late → B shreds Critical material even
    though cancellation exists. Nothing specifies ordering, idempotence, or
    deferral. Also unspecified: whether an authenticated (decoy) session can
    cancel — it must not.

E7. SNAPSHOT + CONFLICT ARCHIVE RESURRECT SHREDDED MATERIAL
    Where: v4 §6.2 + Phase F.2 × v3 §20.1 honest limits
    The last five encrypted snapshots (and conflicts/) still contain wrapped
    DEKs / shares after a shred event. Restoring a snapshot revives
    "destroyed" entries. The honest-limitation clause covers external copies
    — app-controlled local history is not external. Crypto-shredding is
    locally undoable, i.e., false.

E8. BREACH MONITORING HASH MISMATCH — FEATURE CANNOT WORK ONLINE
    Where: status.md Phase K ("5-char SHA-256 prefix") vs HIBP protocol
    Pwned Passwords k-anonymity is keyed on SHA-1 prefixes. SHA-256 prefixes
    never match the API; the offline corpus hash scheme must agree too. The
    online mode is silently non-functional.

E9. PQ-HYBRID CLAIMED, PQ STUBBED
    Where: status.md Phase 0 (ML-KEM-768 stubbed, no liboqs/PQClean) vs
    roadmap Gate 2 + v3 §21.1
    Docs and roadmap mandate X25519 + ML-KEM-768. Shipping classical-only
    while the spec claims PQ is the exact theater the doctrine forbids. No
    gating exists between "PQ present" and "PQ claimed".

E10. NOTHING NATIVE HAS EVER BEEN COMPILED OR VERIFIED ON TARGET
    Where: status.md env blockers (no JDK, no Mint execution, no TPM tooling)
    Kotlin Keystore/autofill/FLAG_SECURE written but uncompiled; seccomp
    never executed (sandbox denial); tray/hotkey native helpers uncompiled;
    real Noise transport unbuilt. EVERY on-device acceptance criterion
    (memory-dump clean on device, ptrace blocked, Keystore invalidation,
    autofill DAL, VmLck) is currently UNVERIFIED. 150 green pure-Dart tests
    prove logic, not delivery.

--- MEDIUM ---------------------------------------------------------------------

E11. TIME-LOCK ENFORCEMENT CLAIM IS FALSE AS WRITTEN
    Where: v4 §6.6 (including the mid-paragraph "Wait. Correction." artifact)
    Seed + iteration count are stored next to the wrapped DEK, so any patched
    build, GPU box, or faster machine recomputes the chain. "Even a patched
    build cannot skip the time-lock because the DEK is mathematically
    inaccessible" is false. It is a CPU speed bump, not access control.

E12. OUTER GCM SEMANTICS AMBIGUOUS (WHAT IS THE PLAINTEXT?)
    Where: v4 §4.3 + Phase A.10
    Header is passed as AAD; the GCM message is never defined. Two
    implementers can build two layouts. Must be explicit: empty-plaintext
    AES-256-GCM over header-as-AAD; the tag IS the header MAC; entry
    payloads authenticate separately under DEK_i.

E13. SSE THREAT MODEL MIS-STATED; REAL LEAK IS TAG COUNT (DOMAIN LENGTH)
    Where: v4 §4.2 / §5.1 / §6.9 / residual risk #15
    Tags are HMAC-SHA256 keyed by SearchKey. Without SearchKey (requires VRK,
    requires MP) they are opaque — a file-only attacker CANNOT test candidate
    domains. The spec's claim "reveals which domains exist to anyone with the
    file" is wrong. The REAL leaks are entry count and domain length (prefix
    tag count = len−2). Wrong threat model → wrong mitigations and wrong
    user decisions.

E14. HAND-ROLLED HKDF VIOLATES THE PROJECT'S OWN DOCTRINE
    Where: status.md Phase 0 ("libsodium lacks crypto_kdf_hkdf_sha256_*")
    The pinned libsodium 1.0.18 exports crypto_kdf_hkdf_sha256_{keygen,
    extract,expand}. The premise is factually wrong; a "no home-rolled
    crypto" project hand-rolled a KDF while the audited primitive sits in
    the loaded library. (Verify by symbol probe; if genuinely absent in a
    build env, fail closed — do not hand-roll.)

E15. BEHAVIORAL BIOMETRICS STATISTICS ARE UNSOUND; FP FIGURE IS FABRICATED
    Where: v4 §6.4 / residual risk #14
    Flight times are right-skewed, not Gaussian; Welford over raw
    milliseconds mis-models them. 50 training samples spread over ~10–15 key
    pairs = 3–5 samples per pair; σ estimates are noise, so the 3σ rule
    fires arbitrarily. The "0.000027% false lock" figure assumes converged
    Gaussians — fiction. MP is typed rarely; convergence takes months.

E16. ADAPTIVE RULE 2 DEFAULT BEHAVIOR ERODES USABILITY ON LAPTOPS
    Where: v4 §6.3 rule 2
    Unknown-network → high posture, on by default. A roaming laptop lives in
    permanent high posture (30 s lock, no biometric, confirm everything) →
    users disable protections. Security that gets turned off protects nothing.

E17. MP-CHANGE RE-WRAP SPEC'D LAZILY AGAINST AN AAD-BOUND HEADER
    Where: v4 §7.9 ("search_tags recomputed automatically at the next unlock")
    The header is AAD-authenticated under one coherent key set. Deferring
    re-wrap/re-tag to "next unlock" creates a mixed-state file (old tags +
    new VRK) that cannot validate. Re-wrap must be atomic at MP-change save
    time.

E18. NOISE PSK OFFLINE DICTIONARY ON LOW-ENTROPY PIN
    Where: v3 §6.1 carried into v4 §3
    PIN-as-PSK: the Noise PSK handshake encrypts under PSK-derived keys, so a
    captured handshake transcript can be tested offline against PIN guesses.
    60 s window + attempt limits stop ONLINE attacks only. A 4–6 digit PIN is
    a weak PSK.

E19. SECCOMP ALLOW-LIST VS THE DART VM = CRASH LOTTERY, NEVER EXECUTED
    Where: v4 Phase B.3 / roadmap Phase 0.3; status.md sandbox denial
    A syscall allow-list must cover the Dart VM's real surface (futex, epoll,
    clone, exec-memory bookkeeping). Hand-writing it is a crash lottery, and
    the filter has never run against the real runtime at all.

E20. BIOMETRIC FAST PATH REMOVES THE DURESS SIGNAL; §7.1 HAS NO SUCH ROW
    Where: v4 §7.1 interaction matrix × Phase D.1; status.md Keystore path
    Duress requires TYPING the duress MP. Android's Keystore/biometric fast
    path bypasses typing, so under a biometric coercion demand the user
    cannot signal duress. The interaction matrix documents duress×backup
    codes but omits duress×biometric entirely.

E21. CANCELLATION CODE STORAGE AND RATE-LIMITING UNSPECIFIED
    Where: v4 §6.2
    8-digit code, shown once — but storage format (plaintext? hash?),
    verification path, and brute-force rate limiting are never defined.

E22. DEAD CODE: v3-FILE COMPATIBILITY BRANCH
    Where: v4 §4.1 vs roadmap Gate 3
    Gate 3 guarantees no v3 file is ever shipped ("no intermediate format is
    ever shipped"), yet §4.1 specifies a v3-file reader. Dead code that still
    demands tests. Fails the project's own deletion test.

E23. MUTATION TESTING MANDATED, NEVER RUN
    Where: roadmap §2.4 / rules_heavy (≥90% kill on crypto + state machines)
    vs status.md (no mutation campaign recorded among the 150 tests).
    The quality gate exists on paper only. No release claim may stand on it.
