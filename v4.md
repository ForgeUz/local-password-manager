Before any implementation, the permanent record of what was considered and killed. This prevents re-litigation.

| Rejected Idea | Kill Reason |

## 4. V4 FILE FORMAT (EXTENSION OF V3 SECTION 3)

The v3 file format is extended, not replaced. Two structural additions.

### 4.1 Vault Count Field

A one-byte field called vault_count is added to the header, immediately after the nonce field.

This field ALWAYS reads the value two, regardless of whether the deniability feature is enabled or disabled.

If deniability is disabled: the second vault slot contains cryptographically random bytes. Any attempt to decrypt it with any Master Password will fail the GCM tag check. It is indistinguishable from noise.

If deniability is enabled: the second vault slot contains a real decoy vault, encrypted under its own VRK derived from the duress Master Password.

An examiner looking at the file header sees vault_count equals two in both cases. Without the duress Master Password, they cannot determine whether the second slot is a real vault or random noise. This makes the existence of the deniability feature itself deniable.

Backward compatibility: a v3 reader that does not understand vault_count will see an unknown field and can reject the file gracefully. A v4 reader encountering a v3 file (no vault_count field) treats it as vault_count equals one and operates normally.

### 4.2 Search Tag Per Entry

Inside each entry's record in the DEK table, a 32-byte search_tag field is added.

search_tag equals HMAC-SHA256 of the normalized domain, keyed by a SearchKey derived from VRK via HKDF with the info string "GENESIS-SEARCH-v4".

The search_tag lives in the header region (inside the DEK table), which is covered by the GCM AAD. This means tampering with any search_tag invalidates the entire file's GCM tag.

The search_tag reveals which domains exist in the vault to anyone who has the file, but does not reveal credentials. This is a documented trade-off: faster search versus domain privacy. Users who prioritize domain privacy over search speed can disable SSE and use full-decrypt search instead.

### 4.3 Complete V4 Header Layout

Magic bytes "GEN4", four bytes. Format version, one byte, value four. KDF algorithm identifier, one byte. KDF memory cost, four bytes. KDF iteration count, four bytes. KDF parallelism, one byte. Salt, sixteen bytes. Nonce, twelve bytes. Vault count, one byte, always two.

Then, for each vault slot (two slots):

Vault identifier, sixteen bytes UUID. Vault type, one byte: zero for primary, one for decoy. DEK table entry count, two bytes. Then for each entry: entry identifier sixteen bytes UUID, tier level one byte, wrapped DEK length two bytes, wrapped DEK variable length, search_tag thirty-two bytes, vector clock variable length, entry ciphertext length four bytes, entry ciphertext variable length padded to size bucket.

Finally: header MAC, sixteen bytes, the GCM tag covering the entire header as AAD.

### 4.4 What Is NOT In The File Format

No steganographic containers. No ORAM structures. No ZK proof fields. No ML model storage. No behavioral biometric data (that lives in a separate encrypted local file, not in the vault). No time-lock metadata for inheritance (that lives in a separate encrypted local file). The vault file contains only vault data.

## 5. CRYPTOGRAPHIC ADDITIONS IN V4

V3's cryptographic specification is unchanged. V4 adds exactly three new derivations, all using primitives already in the v3 dependency set.

### 5.1 Search Key

SearchKey is derived from VRK via HKDF-SHA256 with the info string "GENESIS-SEARCH-v4", producing thirty-two bytes.

SearchKey is derived at unlock time, lives in native secure memory, and is zero-wiped at lock. It is never stored on disk and never transmitted.

search_tag for an entry equals HMAC-SHA256 keyed by SearchKey over the UTF-8 encoding of the normalized domain. Normalization means: lowercase, strip leading "www.", strip trailing slash, apply punycode for internationalized domain names.

For prefix search (typing "git" to find "github.com"), multiple tags are stored per entry: one for each prefix of length three through the full domain length. For a twenty-character domain, this is eighteen tags of thirty-two bytes each, totaling five hundred seventy-six bytes per entry. For one thousand entries, this is approximately five hundred seventy-six kilobytes of tags. Acceptable.

### 5.2 Time-Lock Key

TimeLockKey is computed as an iterative SHA-256 chain: starting from a thirty-two-byte CSPRNG seed, apply SHA-256 sequentially N times.

N is calibrated at creation time by benchmarking SHA-256 speed on the current device and computing how many iterations correspond to the target duration.

The chain is sequential: each iteration depends on the previous output. It cannot be parallelized.

The creator computes the chain once at lock time to derive the key, wraps the target DEK with AES-256-GCM under that key, then destroys both the key and the seed. The wrapped DEK and the metadata (seed, iteration count, creation timestamp, target duration) are stored.

To unlock, anyone with the metadata must recompute the full chain, which takes approximately the target duration of real computation time.

Honest limitation: a faster computer computes the chain faster. The time-lock is calibrated to the creating device's speed. A machine ten times faster unlocks ten times faster. This is acceptable because the inheritance use case is not adversarial timing.

### 5.3 Duress Key Derivation

MK_duress equals Argon2id of the duress Master Password with its own salt and calibrated parameters.

VRK_duress equals HKDF-SHA256 of MK_duress with info string "GENESIS-VRK-DURESS".

VRK_duress decrypts the decoy vault only. The primary vault's VRK is derived from the primary Master Password. The two are independent.

The duress salt is stored in the file header alongside the primary salt. Both are covered by the AAD.

### 5.4 No New Primitives

All three additions use SHA-256, HMAC-SHA256, AES-256-GCM, Argon2id, and HKDF-SHA256. All of these are already in the v3 dependency set. No new libraries are introduced.

## 6. FEATURE SPECIFICATIONS: ALL TWELVE, FULLY DESCRIBED

### 6.1 Honeypot Canary Entries

**Purpose.** Provide a zero-cost detective control that produces unambiguous evidence of compromise.

**Mechanism.** At vault creation, the application generates three canary entries. These entries look like real entries: they have realistic-looking domains (for example, variations on common service names), plausible usernames, and strong random passwords. They are encrypted under their own DEKs exactly like normal entries. They are indistinguishable from real entries in the vault UI.

Each canary entry carries an internal flag marking it as a canary. This flag exists only in the decrypted entry JSON. It is never visible in the encrypted header. The user never sees canary entries in the vault list.

**Trigger condition.** Any access to a canary entry triggers the alarm. Access means: autofill request, reveal request, copy-to-clipboard request, sync read request from a paired device, or any programmatic read of the entry's plaintext.

The normal user never interacts with canary entries. They do not know the entries exist. They never autofill into a canary domain because they never visit that domain. Therefore, any interaction with a canary is evidence that something other than the normal user is accessing the vault.

**Response sequence, in strict order.** First: lock the vault immediately. Second: record a forensic log entry containing the canary identifier, the access method, the timestamp, and the process or API path that triggered the access. Third: send an alert to all paired devices via the existing Noise channel. Fourth: on the next unlock, display a prominent security warning with the forensic details.

**Interaction with sync.** If a canary entry is synced to a paired device and the trigger occurs on that device, the alert is sent to ALL paired devices, not only the device where the trigger occurred.

**Interaction with duress.** If the duress Master Password is entered and the decoy vault is opened, canary checks are suspended for that session. The user under duress should not have the duress flow interrupted by a canary alarm. The canary entries exist only in the primary vault, not in the decoy vault, so this suspension is safe.

**Cost.** Approximately fifty lines of logic. Zero runtime overhead when not triggered.

**Acceptance criteria.** Three canary entries are generated at vault creation. They are not visible in the vault UI. Accessing any canary entry locks the vault, logs the event, alerts paired devices, and shows a warning on next unlock. Normal vault operations never trigger canaries.

### 6.2 Duress Master Password With Silent Alert

**Purpose.** Under coercion, the user provides a fake Master Password that opens a plausible decoy vault while silently triggering protective actions.

**Setup.** During vault creation or at any later time, the user may enable the duress feature. This requires choosing a duress Master Password, which must be different from the primary Master Password. The application derives MK_duress and VRK_duress from this password. A decoy vault is created, encrypted under VRK_duress. The user is prompted to populate the decoy vault with five to ten plausible low-value entries (streaming services, forums, low-stakes accounts). The user is also given a cancellation code, an eight-digit code displayed exactly once, which they must store outside the application.

**Unlock behavior.** When the user enters a Master Password at the lock screen, the application first attempts to decrypt the primary vault. If that fails, it attempts to decrypt the decoy vault using the entered password as the duress password. If the decoy vault decrypts successfully, the application opens the decoy vault and presents it as if it were the normal vault. To the coercer, nothing appears unusual.

**Silent actions triggered by duress unlock.** First: a silent alert is sent to all paired devices via the Noise channel. The alert contains the device identifier, timestamp, and the fact that a duress unlock occurred. Second: crypto-shredding of Critical-tier DEKs in the PRIMARY vault is scheduled with a configurable delay, default two hours. Third: a forensic log entry records the duress event.

**Cancellation.** If the user reaches safety within the delay window, they enter the cancellation code. This aborts the scheduled crypto-shredding and clears the duress alert. If the user cannot cancel (incapacitated, killed), the Critical-tier DEKs are destroyed after the delay expires. Standard and Sensitive entries are NOT shredded because they exist in the decoy vault anyway and destroying them would make the decoy look empty and suspicious.

**Interaction with adaptive security.** When a duress unlock occurs, the adaptive security posture is set to a special "duress" state. In this state, the adaptive engine does not escalate further. The user is already in a coercion scenario. Additional security prompts would blow the duress cover.

**Interaction with behavioral biometrics.** When a duress unlock occurs, behavioral biometrics are disabled for that session. Under duress, the user's typing pattern will be anomalous due to stress. Triggering a behavioral lock would blow the duress cover.

**Interaction with canary entries.** Canary checks are suspended during a duress session. See section 6.1.

**Honest limitation.** If the coercer has BOTH the primary and duress Master Passwords, the defense fails. This is unsolvable at the application layer. If the coercer knows the duress feature exists (for example, by reading this documentation), they can suspect the decoy, but they cannot prove the existence of the primary vault without the primary Master Password. The file format makes both cases structurally indistinguishable.

**Acceptance criteria.** Duress Master Password opens the decoy vault. Silent alert is sent to paired devices. Critical-tier DEK shredding is scheduled. Cancellation code aborts shredding. Adaptive security does not escalate during duress. Behavioral biometrics are disabled during duress. Canary checks are suspended during duress.

### 6.3 Rule-Based Adaptive Security Posture

**Purpose.** Tighten security when the environment looks hostile. No machine learning. No training. No inference. Three deterministic rules.

**Posture levels.** There are three postures: low, high, and lockdown.

**Rule one: canary triggered means lockdown.** If a honeypot canary has been triggered in the current session or was triggered and not yet cleared, the posture is lockdown. In lockdown: auto-lock timeout is zero (immediate lock on any inactivity), biometric fast path is disabled, autofill requires fresh Master Password confirmation for all tiers, Critical entries require fresh Master Password plus FIDO2 hardware key with no shortcuts.

**Rule two: unknown network or recent failures means high.** If the current network is not recognized (the WiFi SSID and BSSID combination has not been seen during a previous successful unlock), or if there have been two or more failed Master Password attempts in the last five minutes, the posture is high. In high: auto-lock timeout is thirty seconds, biometric fast path is disabled, autofill requires one-tap confirmation for all tiers, Critical entries require M-of-N approval as normal.

**Rule three: known network and no failures means low.** If the current network is recognized and there have been no failed attempts recently, the posture is low. In low: auto-lock timeout is five minutes (configurable), biometric fast path is enabled, autofill for Standard tier is automatic with no prompt, Sensitive requires one-tap confirm, Critical requires fresh re-auth as normal.

**Network recognition.** The application stores a list of recognized network identifiers (SSID plus BSSID pairs) in an encrypted local file. A network is added to this list after a successful unlock while connected to it. The list is encrypted under VRK and zero-wiped at lock. The list never leaves the device.

**Posture reset.** Posture resets to low after a successful unlock on a recognized network with no recent failures. Lockdown requires explicit user action to clear: re-enter Master Password after a cooldown period.

**Interaction with duress.** During a duress session, posture is set to a special duress state and does not escalate. See section 6.2.

**Cost.** Approximately eighty lines of logic. Three conditional checks. Zero runtime overhead.

**Acceptance criteria.** Unknown network triggers high posture. Two failed attempts trigger high posture. Canary trigger triggers lockdown. Known network with no failures gives low posture. Each posture correctly adjusts auto-lock timeout, biometric availability, and autofill confirmation requirements. Posture resets correctly after successful unlock.

### 6.4 Statistical Behavioral Biometrics

**Purpose.** Detect if someone other than the owner is typing, based on keystroke timing. This is anomaly detection only, not authentication. It never replaces the Master Password or biometric. It only triggers a re-challenge when the typing pattern deviates significantly from the learned norm.

**What is measured.** Key-pair flight time: the time between releasing key N and pressing key N plus one. This is measured in microseconds. Only flight times are measured. Key hold times are not used. The content of keystrokes is never recorded. Only timing.

**Model.** For each key pair (previous key, current key), maintain a running mean and standard deviation using Welford's online algorithm. This requires storing only three numbers per key pair: count, mean, and sum-of-squared-differences. No model file. No framework. Just arithmetic.

**Training.** The model trains passively during normal Master Password entry. The first fifty key-pair samples are collected without any anomaly detection. After fifty samples, detection activates.

**Detection.** For each new keystroke, compute the z-score: the observed flight time minus the learned mean, divided by the learned standard deviation. If the absolute z-score exceeds three, flag this keystroke as anomalous.

**Response.** A single anomalous keystroke increments a consecutive-anomaly counter. If the counter reaches three consecutive anomalous keystrokes, trigger a lock and require re-authentication. If a non-anomalous keystroke occurs, reset the counter to zero. A single anomaly never locks the vault. Three consecutive anomalies lock it.

**Storage.** The model (all key-pair statistics) is stored in an encrypted local file, encrypted under VRK. It is loaded into secure memory at unlock and zero-wiped at lock. It is never transmitted. It contains no keystroke content, only timing statistics.

**User control.** The user can disable behavioral biometrics entirely in settings. The trade-off is documented: disabling removes anomaly detection.

**Interaction with duress.** Behavioral biometrics are disabled during a duress session. See section 6.2.

**Interaction with adaptive security.** Behavioral biometrics do not change the adaptive posture directly. They trigger a re-authentication prompt, which is a separate mechanism. If the re-authentication fails, the failed attempt count increases, which may trigger the adaptive posture to escalate via rule two.

**False positive rate.** At a three-sigma threshold, the expected false positive rate per keystroke is approximately 0.3 percent under normal typing conditions. The three-consecutive requirement reduces the false lock probability to approximately 0.000027 percent per unlock session. Acceptable.

**Cost.** Approximately two hundred lines of logic. No dependencies beyond basic arithmetic.

**Acceptance criteria.** Model trains on first fifty key-pair samples. After training, anomalous typing (three consecutive z-scores above three) triggers lock. Normal typing does not trigger lock. Model contains no keystroke content. Model is encrypted at rest and zero-wiped at lock. User can disable the feature. Feature is disabled during duress sessions.

### 6.5 Random-Subset Decryption

**Purpose.** When the user accesses a specific entry, also decrypt a random subset of other entries into secure memory, then wipe them. A memory-scraping attacker observing allocation patterns cannot determine which entry was actually accessed.

**Mechanism.** When the user requests access to a target entry (reveal, autofill, copy), the application does the following. First, it decrypts the target entry normally. Second, it selects a random twenty percent of the other entries in the vault. Third, it decrypts those decoy entries into secure memory. Fourth, it uses the target entry for the requested operation. Fifth, it zero-wipes all decrypted data: the target entry and all decoy entries.

**Critical constraint.** Critical-tier entries are EXCLUDED from the decoy set. Decrypting a Critical entry requires M-of-N approval. The random-subset mechanism must not bypass this. Only Standard and Sensitive entries are eligible for decoy decryption.

**Vault size constraint.** For vaults with fewer than five entries, skip decoy decryption entirely. There are not enough entries for the technique to be meaningful.

**Performance.** Decoy decryption happens in parallel with the target entry use. For a vault of one hundred entries, decrypting twenty additional entries with AES-256-GCM adds negligible time (microseconds per entry). For a vault of one thousand entries, decrypting two hundred additional entries adds a few milliseconds. Acceptable.

**Honest limitation.** This is not ORAM. A sophisticated attacker who can observe memory allocation sizes in real time might still infer which entry was accessed based on the size of the displayed result. This technique raises the bar from trivial to requiring active memory monitoring during the exact access window. It is a mitigation, not an elimination.

**Cost.** Approximately forty lines of logic.

**Acceptance criteria.** Accessing an entry decrypts the target plus approximately twenty percent of other non-Critical entries. All decrypted data is zero-wiped after use. Critical entries are never included in the decoy set. Vaults with fewer than five entries skip decoy decryption. No measurable performance degradation for vaults up to one thousand entries.

### 6.6 Time-Locked Secrets Via Hash Chain

**Purpose.** Enable secrets that can only be decrypted after a configurable time period. Used for inheritance (section 6.7) and for tier-downgrade cooling periods.

**Mechanism.** A time-lock wraps a DEK so that it can only be unwrapped after a target duration of computation.

At creation time: generate a thirty-two-byte CSPRNG seed. Benchmark SHA-256 speed on the current device to determine hashes per second. Compute the iteration count as target duration in seconds multiplied by hashes per second. Compute the hash chain: apply SHA-256 sequentially to the seed, N times, producing the TimeLockKey. Wrap the target DEK with AES-256-GCM under TimeLockKey. Destroy the TimeLockKey and the seed. Store the wrapped DEK plus metadata: the seed is NOT stored (it was destroyed). Wait. Correction: the seed IS stored, because it is needed to recompute the chain at unlock time. The TimeLockKey is destroyed. The seed and iteration count are stored as metadata.

At unlock time: anyone with the metadata (seed, iteration count) can recompute the hash chain. This takes approximately the target duration of sequential computation. Once the chain is computed, the TimeLockKey is derived, and the DEK is unwrapped.

**Use for tier-downgrade cooling.** When a user downgrades an entry from Critical to Standard (v3 section 14), the old Critical-tier DEK is time-locked with a short duration (configurable, default twenty-four hours). During the lock period, the entry remains at its old tier. After the lock expires, the old DEK becomes accessible and the tier change takes effect. This replaces the simple "mandatory delay" in v3 with a cryptographic enforcement: even a patched build cannot skip the time-lock because the DEK is mathematically inaccessible until the chain is computed.

**Use for inheritance.** See section 6.7.

**UX during computation.** When unlocking a time-locked DEK, show a progress indicator with estimated time remaining. The computation runs in a background thread. The user can cancel and return later.

**Honest limitation.** A faster computer computes the chain faster. The time-lock is calibrated to the creating device. This is acceptable for the intended use cases.

**Cost.** Approximately one hundred fifty lines of logic.

**Acceptance criteria.** Creating a time-lock wraps a DEK and destroys the key. Unlocking requires recomputing the full hash chain, taking approximately the target duration. The chain cannot be parallelized. Time-lock is used for tier-downgrade cooling. Time-lock is used for inheritance. Progress is shown during computation.

### 6.7 Cryptographic Inheritance Protocol

**Purpose.** If the user dies or is incapacitated, designated heirs can access specified secrets after a time-lock expires. No server monitors liveness. No cloud is involved. The mechanism is purely cryptographic.

**Setup.** The user explicitly enables inheritance. This is off by default. The user selects which entries to include in the inheritance bundle. The user designates one or more heirs. The user chooses a check-in interval (default ninety days) and a grace period (default fourteen days).

The application collects the DEKs of all designated entries into a bundle. The bundle is serialized. The bundle is split into N Shamir shares with threshold K. The shares are distributed to heirs via Social P2P Recovery (v3 section 21.2) or stored on separate physical media (paper QR codes, USB drives). The user chooses the distribution method.

A time-lock is created on the bundle reconstruction key with duration equal to check-in interval plus grace period. The time-lock metadata is stored in a separate encrypted local file (not inside the vault file itself).

**Check-in.** Every time the user unlocks their vault normally, the time-lock is reset: a fresh seed is generated, a fresh chain is computed, the old time-lock metadata is destroyed, and new metadata is stored. This proves liveness. The user does not need to do anything special. Normal vault usage is the check-in.

**Missed check-in.** If the user fails to unlock their vault for the entire check-in interval plus grace period, the time-lock expires. The heir can then activate the inheritance.

**Activation.** The heir collects K of N Shamir shares. The heir obtains the time-lock metadata (stored in the file the user designated, or transmitted via Social P2P Recovery). The heir verifies that the time-lock has expired by checking the creation timestamp against the current date. The heir computes the hash chain, which takes approximately the grace period of computation time. The heir derives the bundle key and reconstructs the bundle from the K shares. The heir extracts the individual DEKs and can now decrypt the designated entries.

**Revocation.** The user can revoke inheritance at any time. Revocation destroys the time-lock metadata and re-encrypts all designated entries under fresh DEKs. The old Shamir shares become useless because the DEKs they protect no longer exist.

**Interaction with Shamir recovery.** The inheritance protocol uses the same Shamir mechanism as v3 section 15.4. The shares are generated and distributed using the same Social P2P Recovery protocol from v3 section 21.2. No new share distribution mechanism is introduced.

**Interaction with zero-recovery.** Inheritance is opt-in. The default remains zero-recovery. Enabling inheritance does not create a backdoor. The vendor never sees the shares, the metadata, or the bundle. The vendor cannot assist in reconstruction. The mechanism is entirely self-custodied.

**Honest limitation.** If the user forgets to check in (for example, a long vacation exceeding the check-in interval plus grace period), the inheritance activates prematurely. The user should set the check-in interval generously. The UX should warn if the user has not unlocked in a long time and inheritance is enabled.

**Cost.** Approximately two hundred lines of logic. Uses time-lock (section 6.6) and Shamir (v3 section 15.4). No new primitives.

**Acceptance criteria.** Inheritance is off by default. Setup requires selecting entries, designating heirs, choosing intervals. Shares are distributed via Social P2P Recovery or physical media. Normal vault unlock resets the time-lock. Missing the check-in interval plus grace period allows activation. Activation requires K shares plus time-lock computation. Revocation destroys metadata and re-encrypts entries. Vendor has no access to any part of the mechanism.

### 6.8 Two-Vault Deniability

**Purpose.** Under coercion, the user reveals a duress Master Password. The coercer gets a plausible vault. The real vault is cryptographically undetectable.

**File format.** The header always contains vault_count equals two. The first slot is the primary vault. The second slot is either the decoy vault (if deniability is enabled) or cryptographically random bytes (if deniability is disabled). In both cases, the header structure is identical. An examiner cannot distinguish the two cases without the duress Master Password.

**Setup.** The user enables deniability mode. They choose a duress Master Password. The application creates a decoy vault encrypted under VRK_duress. The user populates the decoy with five to ten plausible low-value entries. The setup wizard explains the limitations honestly: this is a mitigation, not a guarantee. If the coercer knows the feature exists, they can suspect but cannot prove.

**Unlock flow.** The application tries the entered Master Password against the primary vault first. If GCM tag verification fails, it tries the duress password against the decoy vault. If that succeeds, the decoy vault opens and duress actions trigger (section 6.2). If both fail, the unlock fails.

**Critical constraint.** The order of attempts (primary first, duress second) must not create a timing oracle. Both attempts must take the same amount of time regardless of which one succeeds. This is achieved by always performing both Argon2id derivations and both GCM tag checks, then selecting the result. The total time is constant.

**Interaction with search.** When the decoy vault is unlocked, SSE search operates only on the decoy vault's entries. The primary vault's search tags are not accessible because the primary VRK is not derived.

**Interaction with sync.** The decoy vault is NOT synced. Only the primary vault syncs. The decoy vault exists only on the device where it was created. This is intentional: if the decoy synced, a compromised paired device could reveal the decoy's existence.

**Cost.** Approximately one hundred twenty lines of logic.

**Acceptance criteria.** vault_count is always two in the header. Second slot is indistinguishable from noise without duress MP. Duress MP opens decoy vault. Primary MP opens primary vault. Timing is constant regardless of which vault opens. Decoy vault does not sync. Search operates only on the unlocked vault. Setup wizard explains limitations honestly.

### 6.9 Searchable Symmetric Encryption For Vault Search

**Purpose.** Search the vault without decrypting all entries. Reduces the time the vault's full plaintext exists in memory.

**Mechanism.** At unlock, derive SearchKey from VRK. For each entry, a search_tag is stored in the header (computed at entry creation or update). To search, compute the query token as HMAC-SHA256 of the normalized query keyed by SearchKey. Compare the token against each entry's search_tag using constant-time comparison. Matching entries are returned by identifier. The user must still unlock or reveal the entry to see its contents.

**Prefix search.** For each entry, store tags for every prefix of the domain from length three to full length. When the user types "git", compute the token for "git" and match against all stored prefix tags. This enables instant prefix search.

**Constant-time requirement.** All tag comparisons must use constant-time comparison to prevent timing oracles that could leak which domains exist.

**SearchKey lifecycle.** SearchKey is derived at unlock, lives in native secure memory, and is zero-wiped at lock. It is never stored on disk.

**Privacy trade-off.** The search_tags in the header reveal which domains exist in the vault to anyone who has the file. This is a documented trade-off. Users who prioritize domain privacy can disable SSE and use full-decrypt search, which decrypts all entries into secure memory, performs the search, then wipes everything. Slower, but reveals nothing in the header.

**Interaction with two-vault deniability.** Each vault has its own set of search_tags. When the decoy vault is unlocked, only the decoy's tags are accessible. The primary vault's tags are encrypted under the primary VRK and inaccessible.

**Cost.** Approximately one hundred eighty lines of logic.

**Acceptance criteria.** Search returns results without decrypting non-matching entries. Prefix search works for prefixes of length three and above. All comparisons are constant-time. SearchKey is derived at unlock and wiped at lock. Disabling SSE falls back to full-decrypt search. Search operates only on the currently unlocked vault.

### 6.10 Sync Traffic Padding

**Purpose.** Prevent traffic-size analysis on the P2P sync channel. An eavesdropper should not be able to determine how many entries were synced or how large they are.

**Mechanism.** All sync messages are padded to fixed size buckets: two hundred fifty-six bytes, one kilobyte, four kilobytes, sixteen kilobytes. The message is placed at the start of the bucket. The remaining space is filled with CSPRNG bytes (not zeros, because zeros would be distinguishable).

Additionally, during a sync session, the application sends two to five dummy messages per real message. Dummy messages are random data padded to a random bucket size. They are sent at random intervals between one hundred milliseconds and two seconds. The receiver discards messages that do not match the expected sync protocol format.

**Entry size constraint.** If an entry's ciphertext exceeds sixteen kilobytes (for example, a large secure note), it is split across multiple sync messages, each padded to the sixteen-kilobyte bucket. The receiver reassembles them.

**Honest limitation.** Timing analysis is still possible. An eavesdropper can see WHEN messages are sent, just not their content or size. Full timing resistance would require constant-rate traffic, which is overkill for LAN sync between two devices the user controls.

**Cost.** Approximately thirty lines of logic.

**Acceptance criteria.** All sync messages are padded to bucket sizes. Padding is CSPRNG bytes. Two to five dummy messages are sent per real message. Receiver discards malformed dummy messages. Entries larger than sixteen kilobytes are split and reassembled correctly. An eavesdropper cannot determine entry count or size from traffic observation.

### 6.11 One-Tap Breach Rotation

**Purpose.** When breach monitoring detects that a domain the user has an entry for has been breached, provide a one-tap action to generate a new password and copy it.

**Mechanism.** When breach monitoring (v3 section 18.3) flags a domain, the corresponding vault entry is visually flagged in the UI with a red badge. The Security Dashboard surfaces it prominently. The entry's detail view shows a "Generate and Copy" button.

When the user taps the button: a new strong password is generated using the existing CSPRNG-backed generator. The entry's password field is updated with the new password. The new password is copied to the clipboard with the sensitive flag and thirty-second auto-wipe. The old password is NOT deleted. It is marked as "compromised" in the entry metadata. The user must still manually log into the breached service and change the password there. The application cannot do this automatically. This is consistent with v3 section 21.5's rejection of autonomous credential rotation.

**Interaction with stored TOTP.** If the entry has a stored TOTP seed (v3 section 12.8), the one-tap rotation changes ONLY the password field. The TOTP seed is not rotated. The TOTP seed is a separate factor and is not affected by a password breach.

**Interaction with risk tiers.** The one-tap rotation works for all tiers. For Critical-tier entries, the rotation requires fresh re-authentication before the new password is generated, consistent with Critical-tier access rules.

**Cost.** Approximately sixty lines of logic.

**Acceptance criteria.** Breach detection flags the entry. One-tap button generates new password, updates entry, copies to clipboard. Old password is marked compromised, not deleted. TOTP seed is unaffected. Critical-tier entries require re-auth before rotation. User must still manually update the password on the breached service.

### 6.12 SSH Key Management As Critical-Tier Entries

**Purpose.** Store SSH private keys in the vault with the same per-entry DEK protection, tier system, and multi-device approval as passwords.

**Scope.** This is a v2 feature. It is specified here for completeness but is not part of the v1 implementation.

**Mechanism.** SSH private keys are stored as vault entries with a type field indicating SSH key. The private key material is the payload of the entry, encrypted under the entry's DEK. The default tier for SSH key entries is Critical, which means the DEK is Shamir-split across paired devices (default 2-of-3).

**Agent integration.** On Linux, the application exposes a local Unix socket that acts as an ssh-agent. When an SSH client requests a key, the socket handler prompts for vault unlock (if not already unlocked), then prompts for Critical-tier re-authentication (fresh Master Password, no grace period), then releases the key to the SSH client. The key is held in secure memory only for the duration of the SSH operation, then zero-wiped.

On Android, SSH agent integration depends on platform support. If the platform provides an SSH_AUTH_SOCK equivalent, use it. Otherwise, SSH key management is limited to storage and export.

**Audit logging.** Every SSH key release is logged in the local integrity heartbeat (v3 section 21.4): which key, when, to which process.

**Export.** SSH keys can be exported in PEM format, encrypted under a user-chosen passphrase. The export follows the same MP strength gate as vault export (warn, not block).

**Cost.** Approximately three hundred lines of logic. v2 scope.

**Acceptance criteria.** SSH keys stored as Critical-tier entries. DEK is Shamir-split. Agent integration prompts for vault unlock and Critical-tier re-auth. Key is zero-wiped after use. All releases are logged. Export is passphrase-encrypted. v2 scope, not v1.

## 8. COMPLETE PHASE-BY-PHASE ROADMAP

### Phase A: Crypto Core (REVISED)

This phase establishes the cryptographic foundation. It supersedes the original v3 Phase A flat-blob design with the per-entry key hierarchy from v3 section 19, extended with v4 file format additions.

**Step A.1.** Implement Master Password input buffer in native secure memory via libsodium FFI. The MP is never a Dart String. It is entered into a native-allocated buffer.

**Step A.2.** Implement Argon2id key derivation with adaptive calibration. Calibrate at first run targeting 500 to 1000 milliseconds on desktop, up to 1500 milliseconds on mobile. Enforce hard floor: memory at least 64 MiB, iterations at least 3, parallelism equals minimum of 4 and logical core count. The calibrated parameters (or floor, whichever is higher) are recorded in the header.

**Step A.3.** Derive MK from Argon2id of MP and salt. MK is never used directly as a cipher key.

**Step A.4.** Derive VRK from HKDF-SHA256 of MK with info string "GENESIS-VRK-v4". VRK wraps DEKs. It does not encrypt entries directly.

**Step A.5.** Derive SearchKey from HKDF-SHA256 of VRK with info string "GENESIS-SEARCH-v4". SearchKey is used for search_tag computation. It lives in secure memory and is wiped at lock.

**Step A.6.** At entry creation, generate DEK_i as thirty-two bytes from CSPRNG. Wrap DEK_i under VRK using AES-256-GCM with a fresh CSPRNG nonce.

**Step A.7.** Encrypt entry JSON under DEK_i using AES-256-GCM with a fresh CSPRNG nonce. Pad the entry ciphertext to the next size bucket (4 KiB, 16 KiB, 64 KiB, 256 KiB).

**Step A.8.** Compute search_tag for the entry: HMAC-SHA256 of the normalized domain keyed by SearchKey. For prefix search, compute tags for every prefix of length three through full domain length.

**Step A.9.** Construct the file header per section 4.3 of this document. vault_count is always two. The second vault slot is filled with CSPRNG random bytes if deniability is not enabled.

**Step A.10.** Pass the entire header as AAD to the outer AES-GCM operation. Any tampering with the header invalidates the GCM tag.

**Step A.11.** Implement constant-time comparison for all tag and MAC checks.

**Step A.12.** Verify nonce uniqueness over ten thousand encryption operations. No nonce reuse is permitted.

**Step A.13.** Implement the duress key derivation path: MK_duress from Argon2id of duress MP with duress salt, VRK_duress from HKDF of MK_duress.

**Step A.14.** Implement the time-lock key derivation: iterative SHA-256 chain from seed, N iterations.

**Acceptance criteria for Phase A.** Header tampering causes GCM tag failure, fail-closed, no partial plaintext. MK is never used directly as a cipher key. Nonce uniqueness verified over ten thousand calls. Destroying one DEK renders only that entry unrecoverable. All secrets in native secure memory. search_tag correctly identifies domain without decrypting entry. vault_count equals two with random second slot is indistinguishable from vault_count equals two with real decoy. Duress derivation produces a different VRK that decrypts only the decoy vault. Time-lock chain computation takes approximately the target duration.

**Blocked by.** Nothing. This is the foundation.

### Phase B: Memory and Process Hardening

This phase is unchanged from v3. Restated for completeness.

**Step B.1.** All long-lived secrets allocated via libsodium FFI. Never as Dart String. Never as ordinary Dart Uint8List left to the garbage collector.

**Step B.2.** Explicit zero-wipe on: manual lock, auto-lock timeout, app background, app termination, entry deletion (DEK-specific wipe).

**Step B.3.** Linux: prctl PR_SET_DUMPABLE zero at startup. mlockall to prevent swap. seccomp-bpf syscall filter restricting to necessary syscalls.

**Step B.4.** Android: app sandbox plus hardware-backed Keystore with StrongBox where available.

**Step B.5.** Memory-dump test: in a debug build, after lock, verify no residual plaintext in the process memory.

**Acceptance criteria.** Debug memory dump post-lock shows no residual plaintext. ptrace attach is blocked on Linux. VmLck verified via /proc/pid/status. All secrets in native-backed buffers.

**Blocked by.** Phase A.

### Phase C: Lock, Reveal, and Adaptive Security

This phase combines v3's lock screen and reveal UX with v4's adaptive security, behavioral biometrics, and random-subset decryption.

**Step C.1.** Implement lock screen with MP entry. Rate-limited with exponential backoff on failed attempts.

**Step C.2.** Implement multi-trigger auto-lock: idle timeout, screen-off, app minimize, manual lock. All four triggers are independent. Any one of them locks the vault.

**Step C.3.** Implement per-entry reveal re-authentication with configurable grace period. Standard tier gets the default grace. Sensitive gets a shorter grace. Critical gets no grace, fresh re-auth every time.

**Step C.4.** Implement the rule-based adaptive security posture per section 6.3 of this document. Three rules. No ML. Posture affects auto-lock timeout, biometric availability, and autofill confirmation requirements.

**Step C.5.** Implement statistical behavioral biometrics per section 6.4 of this document. Gaussian model over key-pair flight times. Welford's algorithm. Three-sigma threshold. Three consecutive anomalies trigger lock. Disabled during duress. User can disable entirely.

**Step C.6.** Implement random-subset decryption per section 6.5 of this document. Twenty percent decoy ratio. Critical entries excluded. Vaults with fewer than five entries skip decoys. Zero-wipe all decrypted data after use.

**Step C.7.** Implement the interaction between adaptive security and duress: posture does not escalate during duress.

**Step C.8.** Implement the interaction between behavioral biometrics and duress: biometrics disabled during duress.

**Acceptance criteria.** Rate limiting works with exponential backoff. All four auto-lock triggers function independently. Per-entry reveal respects tier-based grace periods. Adaptive posture changes correctly based on network recognition and failed attempts. Behavioral biometrics detect anomalous typing after fifty training samples. Random-subset decryption includes twenty percent decoys, excludes Critical entries, and wipes all data. Duress disables adaptive escalation and behavioral biometrics.

**Blocked by.** Phase B.

### Phase D: Android Integration

This phase is unchanged from v3. Restated for completeness.

**Step D.1.** Biometric Keystore integration. invalidatedByBiometricEnrollment equals true is mandatory. StrongBox where available. MP always available as fallback. Test: enrolling a new fingerprint invalidates the key.

**Step D.2.** Autofill Service. Verify requesting app origin via Digital Asset Links before returning credentials. FLAG_SECURE on all secret-bearing screens. Inline biometric or MP prompt gates every return.

**Step D.3.** Clipboard. ClipDescription.EXTRA_IS_SENSITIVE on Android 13 and above. Thirty-second auto-wipe timer.

**Step D.4.** Accessibility surface. Secret fields excluded from the accessibility tree where feasible. Documented as a trade-off against screen-reader accessibility.

**Step D.5.** Background and Doze. Session key wiped per auto-lock policy before the OS reclaims or kills the process. Re-unlock required on foreground return. The adaptive security posture's auto-lock timeout must be respected even under Doze constraints.

**Step D.6.** Root detection. Advisory warning shown. Never blocking.

**Acceptance criteria.** New fingerprint enrollment invalidates biometric key. Autofill verifies origin before returning credentials. FLAG_SECURE blocks screenshots and screen recording. Clipboard auto-wipes after thirty seconds. Secret fields are not in the accessibility tree. Session key is wiped before Doze kills the process. Root warning is advisory only.

**Blocked by.** Phase A for D.1. Phase C for D.2.

### Phase E: Linux Integration

This phase is unchanged from v3. Restated for completeness.

**Step E.1.** Global hotkey. Wayland compositor portal GlobalShortcuts API first. X11 fallback with explicit first-run limitation warning about no input-isolation model.

**Step E.2.** Tray icon. Binary locked/unlocked state only. Never renders anything hinting at vault contents.

**Step E.3.** Clipboard. Thirty-second auto-wipe. Sensitivity marking applied where the desktop clipboard manager supports it. Best-effort only. X11 has no native sensitivity concept.

**Step E.4.** TPM 2.0 integration. Seal device-bound second-factor material to TPM PCRs. On machines without TPM, fall back to OS secret store (libsecret, GNOME Keyring, KDE Wallet). Never use an app-private file for device-bound secrets.

**Step E.5.** Wayland input isolation verification. Confirm that the compositor provides input isolation for the application window.

**Acceptance criteria.** Global hotkey works on Wayland. X11 shows first-run warning. Tray shows only binary state. Clipboard wipes after thirty seconds. TPM seals device-bound material. Without TPM, libsecret is used. Wayland input isolation is verified.

**Blocked by.** Phase C.

### Phase F: Backup, Snapshots, Import, Export

This phase is unchanged from v3. Restated for completeness.

**Step F.1.** Manual export gated by MP strength check. Warn, not block, before allowing export of a vault protected by a weak MP.

**Step F.2.** Local Versioned Snapshots. Retain the last five successful encrypted save-states in app-private storage. Oldest-first rotation. Snapshots are taken automatically on every successful save.

**Step F.3.** Third-party CSV import. Read directly via file picker without persisting an extra copy beyond OS temp storage. Prompt the user to securely delete the source file immediately after successful import. Display explicit warning about the plaintext exposure window.

**Step F.4.** Own-format import. Standard MP-gated decrypt.

**Step F.5.** Uninstall protection. Non-dismissible prompt to complete at least one export before the reminder downgrades to periodic soft nudges.

**Step F.6.** Snapshot and 2FA interaction. Snapshots must remain decryptable under the current second-factor material. If 2FA is reset after a snapshot was taken, older snapshots become unopenable with the new seed. This is accepted behavior, documented, not a bug.

**Acceptance criteria.** Export warns on weak MP. Five snapshots retained with oldest-first rotation. CSV import does not persist plaintext beyond OS temp. Own-format import requires MP. Uninstall prompt is non-dismissible. Old snapshots after 2FA reset are documented as unopenable.

**Blocked by.** Phase A.

### Phase G: P2P Sync

This phase combines v3's sync protocol with v4's traffic padding.

**Step G.1.** PQ-hybrid Noise handshake. X25519 combined with ML-KEM-768. PIN used as pre-shared secret in the Noise handshake. Pairing session window sixty seconds or less. Attempt-limited. Cooldown enforced. On success, pin the peer's static public key. TOFU-then-pinned trust model.

**Step G.2.** Per-session ephemeral Noise keys. Forward secrecy per session. No PIN re-entry required after initial pairing.

**Step G.3.** Monotonic per-session counter on every message. Receiver rejects any non-increasing value. Replay protection.

**Step G.4.** Per-entry vector clocks. Each entry carries its own vector clock. Sync operates per-entry. A conflict on one entry does not force a whole-vault conflict. Only the conflicting entry is archived and flagged for manual merge.

**Step G.5.** Conflict resolution. Losing version auto-archived to a conflicts folder. User prompted with manual-merge UI. Preview-before-commit shows a diff: how many entries will be added, overwritten, archived.

**Step G.6.** Sync traffic padding per section 6.10 of this document. Fixed-size buckets. CSPRNG padding. Two to five dummy messages per real message. Random intervals. Entries larger than sixteen kilobytes split across multiple messages.

**Step G.7.** Paired-device review and revocation. Settings screen listing every paired device with its pinned Noise static key, last-synced timestamp, and one-tap revoke. Devices that have not synced in six months are surfaced proactively as stale.

**Step G.8.** Discovery broadcasts throttled. Only one active pairing session at a time. Repeated pairing attempts from the same peer within cooldown are ignored.

**Step G.9.** Sync remains entirely optional. The app is 100 percent functional standalone, offline, forever. Removing the entire sync module leaves a fully working password manager with manual export and import.

**Acceptance criteria.** Passive and active MITM both fail without PIN. Forward secrecy verified per session. Replay counter rejects non-increasing messages. Per-entry vector clocks prevent clock-skew rollback. Traffic padding makes entry count and size undeterminable from traffic observation. Dummy messages are discarded by receiver. Large entries are split and reassembled. Paired-device review shows all devices with revoke option. App works fully offline without sync.

**Blocked by.** Phase A for G.1. Phase C for G.4.

### Phase H: Second-Factor Authentication

This phase is unchanged from v3. Restated for completeness.

**Step H.1.** TOTP vault-unlock 2FA, KDF-bound. The second factor is an input to key derivation, not a UI gate. MK_full equals HKDF of Argon2id of MP and salt concatenated with SecondFactorMaterial. Without correct second-factor material, the derived key is wrong and GCM tag fails. There is no code path to bypass this because it is math, not a check.

**Step H.2.** TOTP seed generation. 160-bit CSPRNG seed. Base32 encoding for QR display. HMAC-SHA1 per RFC 6238 for interoperability with existing authenticator apps. The seed lives in native secure memory. Setup QR display protected by FLAG_SECURE.

**Step H.3.** Backup codes. Ten single-use codes generated at 2FA setup. Shown exactly once. Stored only as Argon2id hashes in a file separate from the vault. Using a valid code disables 2FA for that session and forces re-setup. Exhausting all ten forces regeneration.

**Step H.4.** Companion-device push approval. Reuses the Noise session from Phase G. Number-matching challenge: the requesting device displays a two-digit number. The approving device shows three options. The user selects the matching one. Not a single blind approve button. Rate-limited per cooldown window. Explicit context shown: requesting device name, approximate timestamp. If the paired device is unreachable, falls back cleanly to manual TOTP entry.

**Step H.5.** MFA-fatigue defense. Number-matching plus rate limiting plus explicit context. All three mandatory together. Excess push requests silently dropped, not re-prompted.

**Step H.6.** Stored TOTP for third-party accounts. QR scan or manual Base32 entry. Stored inside the vault entry alongside the password. Undismissable co-location warning at setup. Per-entry toggle to keep the TOTP seed out of this vault. Codes displayed with thirty-second countdown ring. Copy uses sensitive clipboard path.

**Step H.7.** Clock-skew tolerance. Accept codes within plus-minus one time step. Non-blocking warning if clock appears to have drifted significantly.

**Step H.8.** Runtime integrity check on Android. Play Integrity API class. Modified-signature test build triggers visible warning. Does not silently proceed.

**Step H.9.** MP change does not reset 2FA. The TOTP seed is untouched by MP change. Documented explicitly.

**Step H.10.** FIDO2 hardware key as an unlock factor. USB or NFC. The key performs a P-256 signature that is fed into HKDF. Keylogger-immune because no secret is typed.

**Acceptance criteria.** Vault opened with correct MP but wrong or absent TOTP code fails at the GCM tag stage, not at a separate conditional check. Verified by calling the low-level decrypt function directly, bypassing UI, and confirming it still fails. Seed lives only in native secure memory. Backup codes work and are single-use. Push approval requires number-matching. Rate limiting drops excess requests. Stored TOTP shows co-location warning. Clock skew tolerated within plus-minus one step. MP change does not reset 2FA. FIDO2 key works as unlock factor.

**Blocked by.** Phase A for H.1. Phase G for H.4.

### Phase I: Risk Tiers and Wallet-Inspired Hardening

This phase is unchanged from v3. Restated for completeness.

**Step I.1.** Risk-tiered access control. Three tiers: Standard, Sensitive, Critical. Each tier has different reveal re-auth, autofill behavior, push-approval requirements, and quick-copy restrictions per v3 section 14.

**Step I.2.** Default tier heuristics. The app suggests Sensitive or Critical for domains matching known banking, financial, crypto-exchange, or registrar categories. Always user-overridable. Suggestions only, never silent overrides.

**Step I.3.** Tier-downgrade cooldown. Lowering a tier takes effect only after a mandatory delay. In v4, this delay is enforced cryptographically via time-lock (section 6.6). The old DEK is time-locked for the cooldown duration. Notification sent to paired devices. Tier-upgrade is immediate.

**Step I.4.** Autofill preview. One-line confirmation before autofill for Sensitive and Critical entries: "Filling saved login for domain-X into domain-Y." Any mismatch is a hard stop requiring explicit confirmation.

**Step I.5.** Look-alike domain detection. Before autofilling into a domain within a configurable edit-distance or homoglyph threshold of a different saved entry's domain, trigger a hard-stop warning. Exact-match domains are unaffected.

**Step I.6.** Preview-before-commit for sync conflicts and CSV import. Diff view showing how many entries will be added, overwritten, archived. User commits explicitly.

**Step I.7.** Paired-device review and revocation per v3 section 15.8.

**Step I.8.** Shamir recovery kit, opt-in, off by default. Local SLIP-39-class K-of-N share generation and reconstruction. Zero server involvement. Default remains zero-recovery unless the user explicitly enables and completes setup.

**Step I.9.** Capability-based scoped sharing per v3 section 20.4. Time-boxed or single-reveal DEK transmission over the Noise channel. Honest limitation stated in the sharing-confirmation UI: this is receiving-client-enforced, not cryptographically unbreakable.

**Acceptance criteria.** Three tiers implemented with correct policies. Tier-downgrade enforced via time-lock with notification. Tier-upgrade immediate. Autofill preview shows for Sensitive and Critical. Look-alike detection triggers hard stop. Preview-before-commit shows diff. Paired-device review works. Shamir recovery works entirely offline. Capability sharing states limitation honestly.

**Blocked by.** Phase C for I.1. Phase H for I.1 Critical-tier M-of-N. Phase D for I.4. Phase G for I.6. Phase A for I.8.

### Phase J: Coercion Resistance and Deniability (V4 NEW)

**Step J.1.** Honeypot canary entries per section 6.1 of this document. Three canaries generated at vault creation. Not visible in UI. Any access triggers alarm. Response: lock, log, alert paired devices, warn on next unlock.

**Step J.2.** Duress Master Password per section 6.2 of this document. Duress MP opens decoy vault. Silent alert to paired devices. Critical-tier DEK shredding scheduled with configurable delay. Cancellation code aborts shredding. Adaptive security does not escalate during duress. Behavioral biometrics disabled during duress. Canary checks suspended during duress.

**Step J.3.** Two-vault deniability per section 6.8 of this document. vault_count always two. Second slot is decoy or random bytes. Timing-constant unlock. Decoy does not sync. Search operates on unlocked vault only.

**Step J.4.** Decoy vault setup UX. Prompt user to populate decoy with five to ten plausible entries. Explain limitations honestly.

**Step J.5.** Duress setup UX. Create duress MP. Generate cancellation code. Display code exactly once. Explain the mechanism and its limitations.

**Acceptance criteria.** Three canaries generated and hidden. Canary access triggers alarm sequence. Duress MP opens decoy. Silent alert sent. Shredding scheduled and cancellable. Adaptive and behavioral features disabled during duress. vault_count always two. Timing constant. Decoy does not sync. Search scoped to unlocked vault. Setup wizards explain limitations.

**Blocked by.** Phase A for J.1 through J.3. Phase C for J.2 shredding trigger.

### Phase K: Breach Awareness and Security Dashboard

This phase combines v3's breach monitoring with v4's one-tap rotation.

**Step K.1.** Local Security Dashboard. Duplicate password detection across entries. Weak and short password flagging. Password age tracking. All fully local, zero network. Updates incrementally as entries change.

**Step K.2.** Breach monitoring. Pwned Passwords k-anonymity. Default state is off. Enabling requires explicit consent naming exactly what leaves the device: a five-character hash prefix, never the password. Online mode sends the prefix. Offline corpus mode downloads the full dataset for zero-network checking. Offline mode is the preferred default within the opt-in.

**Step K.3.** One-tap breach rotation per section 6.11 of this document. Breach detection flags the entry. Button generates new password, updates entry, copies to clipboard. Old password marked compromised, not deleted. TOTP seed unaffected. Critical-tier requires re-auth.

**Acceptance criteria.** Dashboard flags duplicates and weak passwords locally. Breach monitoring is off by default. Consent names exactly what leaves the device. Offline corpus mode works with zero network at check time. One-tap rotation generates new password, preserves old as compromised, does not touch TOTP seed, requires re-auth for Critical tier.

**Blocked by.** Phase A for K.1. Phase I for K.3.

### Phase L: Time-Locks and Inheritance (V4 NEW)

**Step L.1.** Time-lock puzzles per section 6.6 of this document. Hash chain. Configurable duration. Sequential computation. Progress indicator during unlock.

**Step L.2.** Cryptographic inheritance protocol per section 6.7 of this document. Off by default. Select entries. Designate heirs. Choose check-in interval and grace period. Shamir shares distributed via Social P2P Recovery or physical media. Time-lock on bundle. Normal vault unlock resets time-lock. Missed check-in allows activation. Revocation destroys metadata and re-encrypts entries.

**Step L.3.** Inheritance setup UX. Wizard explaining the mechanism, the check-in requirement, and the revocation process. Warn if the user has not unlocked in a long time and inheritance is enabled.

**Step L.4.** Inheritance activation UX. Heir collects shares. Obtains time-lock metadata. Verifies expiry. Computes hash chain with progress indicator. Reconstructs bundle. Extracts DEKs.

**Step L.5.** Inheritance revocation. Destroy time-lock metadata. Re-encrypt designated entries under fresh DEKs. Old shares become useless.

**Acceptance criteria.** Time-lock computation takes approximately the target duration. Chain cannot be parallelized. Inheritance is off by default. Setup requires explicit action. Normal unlock resets time-lock. Missed check-in allows activation after grace period. Activation requires K shares plus time-lock computation. Revocation destroys metadata and re-encrypts. Vendor has no access to any part.

**Blocked by.** Phase A for L.1. Phase J for L.2 uses Shamir. Phase G for L.2 uses Social P2P Recovery.

### Phase M: SSE Search (V4 NEW)

**Step M.1.** SSE search implementation per section 6.9 of this document. SearchKey derivation. Tag computation. Constant-time comparison.

**Step M.2.** Prefix search. Multiple tags per entry. Prefixes of length three through full domain.

**Step M.3.** Search UI. Instant results without full vault decrypt. Results show entry identifiers and domains. User must still unlock or reveal the entry to see contents.

**Step M.4.** SearchKey lifecycle. Derived at unlock. Wiped at lock. Never stored on disk.

**Step M.5.** Fallback mode. If the user disables SSE, search falls back to full-decrypt search: decrypt all entries into secure memory, search, wipe everything. Slower but reveals nothing in the header.

**Acceptance criteria.** Search returns results without decrypting non-matching entries. Prefix search works for length three and above. All comparisons constant-time. SearchKey wiped at lock. Disabling SSE falls back to full-decrypt search. Search operates only on the unlocked vault.

**Blocked by.** Phase A.

### Phase N: Passkeys and WebAuthn (v2)

This is a major v2 initiative. It requires its own dedicated threat-model pass before scoping into concrete acceptance criteria. It is not detailed here for the same reason P2P sync was not specified until v3 section 6 got a full pass.

**Objective.** The app becomes a WebAuthn platform credential provider. Passkey private keys are stored in the vault as Critical-tier entries. They sync between the user's devices over the existing local P2P Noise channel, not through a vendor cloud.

**Android side.** Credential Manager API integration.

**Linux side.** FIDO2 authenticator implementation.

**Origin binding.** Relying-party origin verification. Resident-key storage format. Attestation handling.

**Blocked by.** Phase A. Phase G. Requires own threat-model pass.

### Phase O: SSH Key Management (v2)

**Step O.1.** SSH keys stored as Critical-tier entries per section 6.12 of this document.

**Step O.2.** ssh-agent integration via local Unix socket on Linux.

**Step O.3.** Per-key usage audit log in the integrity heartbeat.

**Step O.4.** SSH key export in PEM format, passphrase-encrypted.

**Blocked by.** Phase A. Phase C. Phase I.

### Phase P: Integrity and Provenance

**Step P.1.** Local integrity heartbeat per v3 section 21.4. Each session appends a locally-signed, hash-chained log entry: session opened at time T, app version V, binary hash H. A broken chain is evidence of tampering. Detective, not preventive. Low cost.

**Step P.2.** Runtime integrity check on Android per v3 section 12.10. Play Integrity API class. Modified build triggers visible warning.

**Step P.3.** Reproducible builds. Deterministic compilation. Fixed timestamps. Sorted file ordering. Pinned toolchain versions. Published build script and CI logs. Community-verifiable: anyone can rebuild from source and compare the hash against the distributed binary.

**Step P.4.** Binary self-hash verification at startup on Linux. Compare against a known-good hash embedded in a signed manifest. Mismatch triggers advisory warning.

**Blocked by.** Phase A for P.1. P.2 through P.4 are independent.

## 12. IMPLEMENTATION DISCIPLINE

1. One test, one minimal implementation. Tracer-bullet TDD. No speculative code.
2. No new dependencies beyond what v3 already specifies: libsodium, liboqs or pqclean for PQ primitives, Noise protocol library.
3. Every feature has a kill switch. If a feature causes more problems than it solves, it gets removed.
4. Honest limitations stated in the user interface. Decoy vault limitations. Time-lock calibration limitations. Search tag privacy trade-off. Capability sharing limitation. All stated plainly.
5. No feature is added because it sounds impressive. Every feature closes a specific gap in the threat model.
6. Lightweight means: total new code across all twelve v4 features is approximately one thousand two hundred lines. No ML frameworks. No new crypto primitives. No new runtime dependencies.
7. The file format change is backward compatible. vault_count equals two with random second slot is indistinguishable from a single-vault file for any observer without the duress Master Password.
8. All v3 interactions are preserved. MP change does not reset 2FA. Snapshots after 2FA reset are documented as unopenable. Backup codes are stored outside the vault. Decoy vault does not sync. Critical entries are excluded from random-subset decoys. Behavioral biometrics are disabled during duress. Adaptive security does not escalate during duress. Canary checks are suspended during duress.
9. The zero-cloud invariant is absolute. No feature in v4 introduces a server, a cloud dependency, or a network call beyond the existing opt-in breach monitoring (which is off by default and uses only a five-character hash prefix or a fully offline corpus).
10. The zero-recovery-by-design invariant is absolute. Inheritance is opt-in and self-custodied. The vendor never sees, holds, or can assist with any recovery material.
